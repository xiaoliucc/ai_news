# 需求与设计

> 回答"为什么做成这样"。日常操作命令见根目录 `README.md`，功能细节见 [`功能验收清单.md`](./功能验收清单.md)。
> 来源：合并原 `项目计划.md`（2026-08-20 最后一次更新）+ 后续实际实现的校正。最后更新：2026-11-01

## 1. 目标

构建一个 **AI 圈热点情报平台**：自动聚合多个渠道的 AI 热点内容，供个人研究者每天快速扫一遍，并能用自然语言追问。

**演进路径**

| 阶段 | 形态 | 状态 |
|---|---|---|
| MVP | Python CLI，终端输出，3 个数据源 | ✅ 已完成（2026-07-31） |
| 二阶段 | Web Dashboard + AI Agent（采集→SQLite→FastAPI→Vue 四层） | ✅ 已完成（Phase 0-5） |
| 当前 | 单机自部署全栈（Docker 单容器 + 可选公网隧道），6 个数据源，Agent 六工具 | ✅ 已完成（2026-09-06） |

**非目标**（有意不做，避免误解为欠缺）

- 不做多用户 / 注册登录：单用户自部署语义，各部署者自填各 key（公网暴露时用可选 `API_TOKEN` 挡扫描器）。
- 不做数据源动态注册：源清单在代码里，UI 只做启停（`selected_sources`）。
- 不做数据库选型折腾：SQLite 单文件 + WAL 足够个人量级（当前 3773 篇 / 71 轮）。
- 不引入 LangChain 等编排框架：tool-use 循环 100 行内可读可控。

## 2. 架构

四层单向依赖：采集层 → 存储层 → API 层 → 展示层，Agent 横跨存储与 API。

```
采集层  Scheduler(APScheduler) + NewsEngine + 6 个 SourcePlugin
          ↓ 并发 fetch → 去重 → 排序 → LLM 相关性/质量判定
存储层  SQLite（articles / collection_runs / user_profile，WAL）
        ChromaDB（语义索引，sentence-transformers 嵌入，384 维）
          ↓
API 层  FastAPI（/api/articles · /sources · /stats · /collect · /agent/chat(SSE) · /health）
          ↘ AI Agent（LLM + 6 工具 tool-use loop，最多 5 轮）
展示层  Vue 3.5 SPA（Vite + TS + Element Plus + Pinia + vue-echarts，三栏 Dashboard）
```

**目录职责**（与 `README.md` 架构段一致，此处只说明边界）

- `src/` — 无 web 感知的数据管道：模型、源插件、引擎、排序、LLM、CLI 入口。
- `backend/` — FastAPI、SQLite、调度器、向量库、Agent；依赖 `src/`。
- `frontend/` — 纯展示，全部数据经 `src/api/` 的 axios 层获取。

## 3. 技术选型与理由

| 组件 | 选择 | 理由 |
|---|---|---|
| 包管理 | `uv` | Rust 实现，比 pip 快一个数量级；`uv.lock` 可复现 |
| CLI | `click` | 装饰器风格，命令组支持子命令 |
| HTTP | `httpx` | 原生异步，与 `asyncio.gather` 并发采集契合 |
| 解析 | `beautifulsoup4` + `lxml` | 仅 GitHub 源需解析静态页 |
| 异步 | `asyncio` | 六源并发；`gather(return_exceptions)` 容忍单源失败 |
| 调度 | `apscheduler`（AsyncIOScheduler） | 进程内调度，无需系统 cron |
| 数据库 | `sqlite3` 标准库 + WAL | 零配置单文件；读写并发够用 |
| 向量 | ChromaDB + `paraphrase-multilingual-MiniLM-L12-v2` | 中文查询命中英文内容；本地离线可跑 |
| API | FastAPI + uvicorn | 异步原生、自动 OpenAPI |
| 前端 | Vue 3.5 + Vite + Element Plus + ECharts + Pinia | 复用 OpenDesign 设计稿（`endfield-ai-intel-dashboard`），UI 层零改动接入真实 API |
| LLM | OpenAI 兼容端点（当前 `deepseek-chat`） | 可换供应商只改 `.env`；`_chat_json` 统一出口便于降级与重试 |

## 4. 数据模型

```python
@dataclass
class Article:
    id: str                    # 唯一标识 source:source_id（如 arxiv_2401.12345）
    title: str
    url: str
    source: str                # hackernews / arxiv / huggingface_papers / rss / github / csdn
    summary: str
    author: str | None         # GitHub 源填 owner；其余多数为空
    published_at: datetime | None   # 缺失时回退采集时刻（GitHub/CSDN 语义即"今天"）
    score: int                 # 热度：HN upvotes / GitHub 今日 star / CSDN 浏览量
    tags: list[str]            # 语言、方向
    language: str              # en / zh
    quality: float | None      # LLM 质量分 0-100，降级时为 None
```

三条不变量：

1. **`score` 不跨源比较**：各源量纲不同，`ranking` 先做同源 min-max 归一化。
2. **`published_at` 尽量真实**：GitHub trending 无发布时间 → 取采集时刻（榜单语义即"今天"）；topics 页取行内 `relative-time`。
3. **`quality` 可空**：LLM 不可用时为 `None`，`rank()` 的质量因子回退 1.0（即 v1 公式）。

## 5. 数据源策略

| # | 源 | 内容 | 接口 | 热度口径 | 备注 |
|---|---|---|---|---|---|
| 1 | hackernews | Top Stories 中过滤 AI 相关 | Firebase API，免费无认证 | upvotes | 详情并发拉取 |
| 2 | arxiv | cs.AI/CL/CV/LG 新论文 | 官方库，免费 | 论文分值（多为 0） | 1s 限速 |
| 3 | huggingface_papers | HF 每日论文 | `huggingface.co/api/papers` | 无 | 原 Papers With Code 已被 HF 收购 |
| 4 | rss | 通用 RSS/Atom 聚合 | `RSS_FEEDS` 配置 | 无 | 现挂机器之心官方 RSS（免费额度：60 分钟/次、每日 25 次、单次 10 条） |
| 5 | github | trending + explore + topics 活跃榜 | 解析静态页，无官方 API | 今日新增 star（coverage 页 score=0） | 需代理；`score=0` 防量纲混用 |
| 6 | csdn | 博客热榜 | 前端自用 JSON 接口（无文档但稳定） | 浏览量 | 国内直连，`trust_env=False` 禁读代理 |

**扩展方式**：实现 `SourcePlugin.fetch()` 后在 `SOURCE_REGISTRY` / `SOURCE_META` 注册。实测失败过的候选源（知乎需登录、公共 RSSHub 不可用、机器之心 HTML 改付费）见 [`踩坑与已知问题.md`](./踩坑与已知问题.md)。

## 6. CLI 设计

CLI 与 Web 共用引擎，但**保持三源**（HN / ArXiv / HF）——它是"跑一次看结果"的轻量入口，不承担全量采集。

```bash
uv run python -m src.main fetch                             # 默认全源，终端表格
uv run python -m src.main fetch -s hackernews,arxiv --limit 30
uv run python -m src.main fetch -o markdown -f daily.md      # 输出到文件
```

## 7. 关键设计决策

| 决策 | 结论 | 理由 |
|---|---|---|
| Agent 实现方式 | 手写 tool-use loop（非 LangChain） | 5 轮 + 6 工具规模下，框架带来的抽象成本高于收益；循环逻辑 100 行内可读 |
| LLM 调用出口 | 所有调用走 `src/pipeline/llm._chat_json` | JSON 模式 + temperature=0 + 指数退避重试集中一处；降级（关键词匹配 / quality=None）也只在这里 |
| 排序公式 | `归一化score × 时间衰减(48h 半衰期) × 源权重 × 质量修正(0.7~1.0)` | 热度可比、时间可比、源可信度可调；质量因子复用已有 LLM 判定，零额外成本 |
| 记忆分层 | P0 用户偏好（`user_profile`）→ P1 阅读历史（上限 50）→ P2 对话摘要（超 12 条归档进 `conversation_summary`） | 从"确定事实"到"模糊回忆"分层，避免上下文膨胀 |
| 源管理 | UI 启停 + `selected_sources`（空=全选） | 比动态注册简单；CLI 不受影响 |
| Agent 输出 | SSE 真流式（`tool`/`token`/`done`/`error`） | 首 token 延迟大幅下降；工具进度真实上报而非前端猜测 |
| 公网暴露 | 可选 `API_TOKEN` 中间件（留空=关闭） | 单用户语义下不做多用户鉴权；只需要挡住扫描器与额度盗刷 |
| 部署 | Docker 单容器（前端 dist + API + 调度器，端口 8000） | 无云服务器也能一键起；将来迁服务器只需 compose |

## 8. 引擎演进（供理解代码形状）

```
v1  run():  gather 拉取 → 按 id 去重 → sort(score) → 输出
v2  run():  gather 拉取 → dedup(arxiv 指纹) → rank(复合) → EngineResult
v3  backend 模式：上述结果 → 入库 SQLite → 入索引 ChromaDB → API/Agent 读取
```

`EngineResult`（articles + 各源 source_stats + deduped_count + 耗时）是给 Dashboard 的结构化统计出口；`src/` 至今不感知 web。
