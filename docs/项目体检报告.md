### H-2-4 同一组筛选条件执行两次

**证据**
```text
后端 backend/database.py:222-231
    WHERE collected_at >= cutoff  AND source IN (...)  LIMIT ?
前端 frontend/src/stores/articles.ts:97-110
    if (a.published_at && Date.parse(a.published_at) < timeCutoff) return false

```

**原因**：`filteredArticles` 同时承担"客户端搜索/排序"和"服务端条件再校验"两种职责。

## 4. 绕来绕去 / 过于复杂的调用

### H-4-1 请求路径上的 N+1 查询（真实性能点）

**证据** `backend/routers/agent.py:47-61`
```python
def _resolve_titles(article_ids: list[str]) -> list[str] | None:
    titles = []
    for aid in article_ids:          # 最多 50 条（reading_history 上限）
        a = get_article(aid)         # 每条一次 SQLite 查询 + 一次连接
        if a is not None:
            titles.append(a["title"])
```
调用点在第 93 行，位于**同步函数体**内、`StreamingResponse` 建立之前 → 每次发消息都要先串行查 N 次库。

**原因**：`reading_history` 只存 ID，展示/注入需要标题，就地循环最直观。

**影响范围**：N 最大 50，单次查询 ~0.1ms 级，绝对耗时不大（<10ms），但它是"每次对话的第一段延迟"，且 `get_article` 每次走 `_get_connection()`。在 Agent 首 token 已经 1s 量级的情况下不是瓶颈，属于"该顺手修"而非"必须修"。

**建议**：加 `database.get_articles_by_ids(ids) -> dict`，一条 `WHERE id IN (...)` 拿回全部；或把 `reading_history` 改成存 `(id, title)` 对，彻底省掉反查。

## 6. 安全问题

### H-6-1 【高】Agent 回答用 `v-html` 渲染，未做消毒 → 存储型 XSS 面

**证据**
```text
frontend/src/components/MessageBubble.vue:26-29
    const rendered = computed(() => {
      const text = props.streamingText ?? props.message.content
      return marked.parse(text, { async: false, breaks: true }) as string
    })
frontend/src/components/MessageBubble.vue:54-57
    <div class="bubble__content markdown" v-html="rendered"></div>

package.json dependencies：无 DOMPurify / sanitize-html（marked v12 已移除内置 sanitize）
```

**攻击链**（不需要攻击者拿到账号，只需要污染数据源）
```
恶意/被篡改的 RSS 条目标题或摘要
  → 采集入库（后端不消毒，合理：数据层不该做 HTML 消毒）
  → Agent 检索到并原样引用进回答（LLM 会把标题贴回来）
  → 前端 marked 渲染 → v-html 注入 → 脚本在当前源执行
```

**影响范围**：脚本运行在应用同源上下文，可读取 `localStorage`（当前只存主题/语言，一旦以后存 token 就会被窃取）、可带上用户身份调用任意 `/api/*`（当前 `API_TOKEN` 为空，等于无门槛）、可篡改页面呈现的新闻内容（情报类应用的信誉损失比数据泄露更直接）。

**原因**：`marked` 只做 Markdown → HTML，从不负责消毒；这是"渲染富文本"最常见的漏项。

**建议**（按成本从低到高）
1. 立刻：`npm i dompurify`，`v-html="DOMPurify.sanitize(rendered)"`（白名单默认即可挡住 `<script>`/`onerror`/`javascript:`）。
2. 加固：不要对 LLM 输出放开原始 HTML——配置 marked 只允许行内 Markdown，或渲染后过一遍 `sanitize(..., {ALLOWED_TAGS: ['p','ul','ol','li','strong','em','code','pre','a','h1'..'h4']})`，并对 `<a>` 强制 `rel="noopener noreferrer"`（当前注释里已提到 `<a>` 由 v-html 生成）。
3. 兜底：加 CSP `default-src 'self'; script-src 'self'`（当前无任何安全响应头）。
